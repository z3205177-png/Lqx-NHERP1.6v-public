# 候选编码推测逻辑

默认审核已按2026-10-25最新确认更新：原编码已收录、无明确冲突即通过，信息不足也通过。v1.6默认给异常与空编码生成独立推测列；其中历史450条统计不作为当前核验状态。

2026-10-25，用户查看《待确认商品清单及推测商家编码.xlsx》后反馈：“你推测的基本上都是对的，记住这套推测逻辑”。该反馈认可候选生成方法；没有指定全部正确的SKU或错误例外，不能当成所有候选的逐条确认，也不能计算准确率。

## 使用步骤

1. 读取真实平台行及组合装、单品两份ERP，保留原始来源、ID、SKU、原编码和源行号。以SKU选定属性为主要规格证据；标题用于辨认品类和生成线索。产品分组可以参考当前编码的ERP名称，但这种参考不证明编码正确。
2. 若原编码在合并ERP中唯一命中，检查该记录与平台明示规格是否相符。通过下面的候选筛查后，才将它保留为待审候选；原编码存在本身不构成正确证据。
3. 排除明示数量、配方、材质、性别或尺码类型、颜色、字母尺码、容量和数字尺寸冲突。属性未提供与属性冲突分别记录；未知款式别名可以作为待确认问题保留，不能因此认定同一商品。
4. 根据品类补查必要线索。其他编码也必须来自本次真实ERP库，不能拼接、推算或杜撰编码。证据不足、仍有冲突或无法选出可支持的候选时，推测列留空并写清原因。
5. 按共性业务关系分组，让用户确认款式别名、数量档、尺码对应或套装组成及其适用范围、例外。规则接入程序并通过回归验证后，才能作为自动判定依据；不能让每条候选仅因属于同组就自动变成已确认。

## 本次实现的品类筛查

| 品类 | 保留候选所需的支持 | 仍需核实的边界 |
|---|---|---|
| 鞋垫、暖贴、暖手足宝、足贴、艾灸、部位热敷、眼罩、冰凉贴 | 平台与ERP品类相关，总数量可一致核对；眼罩另查香型和混合装文字 | 款式别名、同量不同商品、包装和赠品仍可能存在歧义 |
| 护膝、护腰套装 | 主品部位、字母尺码、搭配暖贴片数有对应；明示颜色无冲突 | 尺码别名及实际套装关系仍需确认 |
| 手套 | 手套品类、字母尺码和总只数可核对，明示材质颜色无冲突 | ERP只写S/M/L而不写总只数，不凭重量反推数量 |
| 热水袋 | 热水袋品类及容量、数字尺寸或外形款式词有对应，明示规格无冲突 | 同色不充分证明同款；兔、熊等词仅支持候选，不能证明具体型号 |
| 高筒PVC鞋套 | 本批939型号已确认，候选透明色有对应 | 字母尺码与ERP数字范围仍未确认；S、M、5XL缺候选时留空，不套用919尺寸表 |
| 鼠标垫、围挡及其他跨产品组合 | 本次实现没有足够的部件、功能和型号对应关系 | 保持推测为空，补齐关系后再扩展 |

单位换算仅沿用已确认范围：足贴、发热鞋垫、暖手足宝按1对=2片。三合一混合装按已确认规则比较总数，继续区分ERP单配方；本批7条三合一10片与KTCP02501单配方艾草10片的冲突继续保留供处理，在v1.5列为商品/规格不一致异常。该规则不延伸到眼罩混合装。

原编码指向错误颜色的护膝/护腰记录，另在全库筛查主品、颜色、尺码及搭配暖贴片数；本次只有恰好一个通过筛查的ERP行时才列为替代候选，仍不等于商品身份已经确认。本次没有为所有留空记录穷尽全库替代方案，后续可增加有证据支持的检索路径。

## 输出与证据

- 原编码保留原值。推测码单列，附ERP名称、来源行和推测依据或留空原因；确认结果和用户填写编码另设列。
- 推测候选可以与原编码相同，表示它通过本次候选筛查；不等于全库唯一或最终“编码正确”。候选生成过程可能暂留款式或品类文字差异供审核，最终状态按SKILL中的最新原编码审核口径处理；推测的替代编码本身仍需明确关系。
- 空编码、无匹配和冲突保留原行。确认前不填“应改为编码”，不自动更新已确认映射。
- 本次证据为450条未决SKU、30个规则主题：348条有候选、102条留空。其中342条候选沿用原编码，6条咖色护膝原编码指向灰色，另找到了颜色、尺码及搭配片数相符的ERP候选。这是候选覆盖情况，不是匹配准确率，也不代表当前引擎的最终状态统计。
- 当时实现：工作区`work/prepare_review_450.py`；复核中间数据：`work/review_450_prepared.json`；交付：`outputs/待确认商品清单及推测商家编码.xlsx`。这些路径相对于外层工作区，供维护者追踪实现；本参考记录的方法不依赖这些临时文件才能阅读。

历史450条使用临时脚本；v1.6已将候选筛查、限定确认关系、多候选和留空处理接入通用Python引擎suggest_code_candidates。用户“基本都对”的认可用于继续采用该方法；新业务映射仍按明确确认的适用范围实施。

## v1.6交付约定

异常及空编码默认追加推测列，原编码及原状态保持不变。一个有支持的ERP候选填主推测码，多个则主列留空、其他候选列完整列出；无可靠候选留空。原核验已有明确补录码的直接列出。优先使用有效且范围一致的确认关系，缺关系时按本次真实ERP规格筛查；不生成不存在的码，不将不同材料或主赠品组合装作为单款候选。替代码列仅供审核，不写入confirmed_mappings。新增异常及补录推测页集中展示，旧450条候选表不替代本次真实复跑。

## v1.7默认交付

固定ERP未获用户更新通知时一直复用登记版本；只输入平台文件即可完成核对和简版导出。默认两表、基础9列加3候选栏，候选格显示编码及ERP原名称。候选按具有相同明示值的规格证据数量排序，相同证据并列，以编码作稳定次序；不是正确性分数或概率。候选集合及主推测列填写条件保持不变。完整候选和证据保存在输出旁的核验依据JSON。交付物生成即完成任务，不要求用户回传确认、修改平台或再次导出复核。
